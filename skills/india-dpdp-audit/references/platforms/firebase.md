# Firebase playbook

Use alongside the generic and any storefront playbooks when Firebase participates in a sampled flow. Sources: [delete user data extension](https://firebase.google.com/docs/extensions/official/delete-user-data), [Firestore TTL](https://firebase.google.com/docs/firestore/ttl), [rules conditions](https://firebase.google.com/docs/firestore/security/rules-conditions), [API keys](https://firebase.google.com/docs/projects/api-keys), [rules unit tests](https://firebase.google.com/docs/rules/unit-tests). Accessed 2026-11-18; recheck before use.

## Developer procedures

**FBR-01 — data map.** Request a redacted mapping from each sampled client field and purpose to Auth UID, Firestore document and subcollection paths, Storage objects, other services and external recipients. Include identifiers that are not the UID and actual notice and consent-state handling. App and privacy owners trace a synthetic staged event through the client and server; compare the event with the inventory and disclosures. A Firebase client configuration or API key is not alone proof of data access or a secret leak.

**FBR-02 — deletion coverage.** Request installed Delete User Data extension configuration, Firestore/Realtime Database/Storage paths, `{UID}` substitutions, auto-discovery settings if used, and Firestore delete mode. Compare each configured target with the cross-system UID map, including identifiers that do not match a UID. The extension acts on configured data; default Firestore deletion is shallow, while its `recursive` mode covers subcollections of configured documents. It does not cover unrelated stores automatically. Review Firestore TTL policies and expiry fields separately: TTL is asynchronous and deleting a document through TTL does not delete its subcollections. Map exports, backups, downstream recipients, legal holds and their expiry or deletion mechanism.

Data engineer and privacy operations fill demonstrated gaps and run a synthetic deletion in authorized staging. Verify the Auth identity, each mapped document and descendant, object and downstream copy independently, recording timing, errors and retained exceptions. Auth deletion, configured paths or a TTL timestamp alone is not a complete deletion test; an unprovided configuration remains unknown.

**FBR-03 — client and server authorization.** Request the deployed rules version and repository configuration: inspect `firebase.json` for the actual rule file paths and databases, commonly `firestore.rules` and `storage.rules`, then compare with deployed rules. Check client read/write conditions for ownership, role and field constraints. Firestore server client libraries bypass Firestore Security Rules: separately inspect backend identity verification, authorization checks, service-account privileges and IAM. Request redacted deployment and IAM evidence; avoid treating local source as deployed state.

Security/backend owners repair the evidenced control and use the [Firebase Emulator Suite](https://firebase.google.com/docs/emulator-suite/install_and_configure) and [rules unit tests](https://firebase.google.com/docs/rules/unit-tests) with synthetic identities. Assert permitted owner operations succeed and unauthenticated, cross-user and unauthorized role/field operations fail for both relevant data stores; test server authorization separately. Record actual emulator configuration and results, then verify deployment separately. Never probe production without specific authorization.

**FBR-04 — rights and recovery.** Request redacted request routing, completion and incident/recovery exercise evidence, plus audience and guardian-flow evidence if children's processing is relevant. Privacy operations run a synthetic request through every mapped recipient and document exceptions; product and security owners verify applicable guardian and recovery flows. A contact link or callable function alone does not prove completion.
